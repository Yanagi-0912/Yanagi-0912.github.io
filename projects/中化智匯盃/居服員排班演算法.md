# 居服員排班演算法
---
## 1. 問題形式化

### 輸入

**服務個案 'j'**

| 參數 | 說明 |
| --- | --- |
| `[e_j, l_j]` | 時間窗（最早可開始、最晚可開始） |
| `d_j` | 服務時長 |
| `g_j` | 長照等級 |
| `r_j` | 服務收費（由長照等級決定） |
| — | 技能／性別／性格需求 |
| — | 指定居服員、排除（黑名單）居服員 |
| — | 前次服務之居服員 |

**居服員 'w'**

| 參數 | 說明 |
| --- | --- |
| `t_w` | 薪資類型（月薪／時薪／拆帳） |
| — | 薪資費率 |
| — | 當日可出勤時段 |
| — | 住家位置（選填；不進入成本與工時計算，僅供通勤負擔參考） |
| — | 具備技能、性格 |
| — | 法定工時上限 |

**環境**

* `τ(i, j)`：地點 i 到地點 j 的轉場（交通）時間矩陣

### 決策變數

* `x_{w,i,j} ∈ {0,1}`：居服員 w 是否從個案 i 直接前往個案 j
* `s_j`：個案 j 的實際開始服務時間

### 問題結構

每位居服員的一日行程構成一條路線：

```
住家（起點） → 個案 → 個案 → … → 住家（終點）
                └── 首末段為通勤，不計成本與工時 ──┘
```

亦即 multi-depot VRPTW，需在滿足所有限制下決定
「哪些個案由誰服務」與「以什麼順序服務」。

## 2. 建圖與可行邊剪枝

每日為當日所有個案繪製一張有向圖，節點為個案，
並將轉場時間上不可能銜接的路徑排除。

### 可行邊判定式

```
邊 (i → j) 存在  ⟺  e_i + d_i + τ(i, j) ≤ l_j
```

以個案 i 的**最早開始時間**加上服務時長與轉場時間，
若仍晚於個案 j 的**最晚開始時間**，則此銜接在任何情況下都不可行，該邊直接刪除。

> 範例：第一個個案時間窗 7:00 ~ 7:10、服務時長 90 分鐘，
> 第二個個案時間窗 8:10 ~ 8:20，兩點之間需 20 分鐘轉場。
>
> `7:00 + 90 + 20 = 8:50`，已晚於第二個個案的最晚開始時間 8:20，
> 即使第一個個案以最早的 7:00 開始也來不及，此邊直接刪除。
>
> 若服務時長改為 60 分鐘，則 `7:00 + 60 + 20 = 8:20`，恰好可行 ——
> 但第一個個案必須準時 7:00 開始，毫無緩衝。

### 拆解目標

假如當日有 n 名居服員可以出勤，
則須將此有向圖以較低成本拆成 n 條互不重疊的路線。

## 3. 目標函數

不只最小化轉場時間，而是在**營運毛利**與**員工公平／個案偏好**之間取得平衡。

由於毛利的單位是「元」、罰分是 0~1 的無量綱指標，兩者不能直接相減，
因此先各自正規化後再加權：

```
max   F = (1 − θ) * Π_norm  −  θ * P  −  ρ * u

  Π      = Σ_j r_j − Σ_w C_w − c_travel        當日毛利（元）
  Π_norm = Π ÷ Π_ref                           Π_ref = 當日所有案件收入總和
  P      = λ1*P_fair + λ2*P_pref + λ3*P_idle   ∈ [0, 1]，λ1 + λ2 + λ3 = 1
  θ      ∈ [0, 1]                              營運 ↔ 員工 的取捨
  u      = 未排入案件數 ÷ 總案件數              ρ 為固定懲罰係數（暫定 0.5）
```

* `c_travel`：交通成本（轉場次數與里程的影響全數計入此項）
* `Π_ref`：以當日所有案件的收入總和為尺度基準（當日為定值），
  使 `Π_norm` 與 `P` 落在可比較的量級
* `θ`：單一取捨旋鈕 —— `θ = 0` 純粹追求毛利，`θ = 1` 完全以公平與偏好為優先。
  管理者可直接理解為「我願意放棄多少比例的毛利，換取更公平的排班」
* `λ1 ~ λ3`：罰分內部的相對權重，控制公平、偏好、空班三者孰輕孰重
* `ρ * u`：未排入案件的懲罰項。**此項不可省略** —— 當 `θ = 1` 時毛利權重為 0，
  若無此項，「什麼都不排」會得到 `P_fair = P_idle = 0` 的最佳解，形成退化解

> **月薪為沉沒成本**：月薪居服員的當日成本無論是否排入案件、
> 甚至當日請假，皆須計入 `Σ_w C_w`。若僅計入有排班者，
> 會出現「讓月薪員工請假可提高毛利」的錯誤結論。

> `P_fair`、`P_pref`、`P_idle` 三項的定義與分值見「基本設計.md → 罰分」。
> 管理員介面的權重面板即對應 1 個 `θ` 與 3 個 `λ` 滑桿，皆為 0~1。

> **首末段通勤的處理**
> 居服員自住家出發前往第一個個案、以及自最後一個個案返家，
> 依法屬通勤而非工作，因此**既不計費、也不計工時**：
>
> * 不計入 `c_travel` 交通成本
> * 不計入時薪的給付時數
> * 不計入法定工時上限與壓力指數的連續工作時數
>
> 換言之，首末段在最佳化中不產生任何成本、也不佔用工時額度。
> 排班時僅需確保**第一個個案的開始時間**與**最後一個個案的結束時間**
> 落在該居服員的可出勤時段內，通勤在此時段之外，由居服員自行安排。
>
> 因此住家位置不影響排班的可行性判定，
> 僅在需要衡量「長期通勤負擔是否公平」時作為參考資料。

### 人力成本 C_w 依薪資類型而異

| 薪資類型 | 成本 `C_w` | 對排班的含意 |
| --- | --- | --- |
| 月薪 | 固定，**邊際成本 ≈ 0** | 在合法工時內盡量排滿，可直接提升人均產值 |
| 時薪 | 費率 ×（服務時數 + 轉場時數，不含首末段通勤） | 轉場也在耗費成本，路線必須緊湊 |
| 拆帳 | 拆帳比例 × `r_j` | 成本與收入連動，毛利率固定 |

### 核心洞察

**三種薪資類型的「邊際毛利」不同**，因此高單價（高長照等級）的個案
優先指派給月薪居服員，才是全域最優解 —— 這正是本問題中 Knapsack 的部分。

人工排班幾乎不可能同時將收費級距、薪資結構、轉場成本一併納入計算，
這是 AI 排班相對於現行作業最直接的效益來源。

> 反向約束：月薪居服員不得無限排滿，
> 受《勞動基準法》單日工時上限與休息時間規定硬性限制。

## 4. 硬約束與軟約束

兩者必須分開處理：硬約束若僅以罰分處理，族群中將充滿無效解，GA 難以收斂。

| 硬約束（由編碼或修復機制保證） | 軟約束（計入罰分） |
| --- | --- |
| 服務時間窗 | 未指派指定居服員 |
| 同一居服員時段不得重疊 | 未延續前次居服員（照護連續性） |
| 排除／黑名單居服員 | 壓力指數分配不均（已含工時分配） |
| 技能、性別需求 | 空班時間 |
| 法定工時上限與休息時間 | 性格配對度不佳（暫緩，改由 §6 的 LLM 前處理產生，現階段不計入罰分） |
| 轉場時間可行性 | —（轉場成本已由目標函數 c_travel 直接計入） |

## 5. GA 設計

### 染色體編碼

* 染色體 = 當日所有個案的一個排列
* 解碼時以動態規劃（Split）將排列切成 n 段，各段指派給一位居服員
* 交配運算子：OX / PMX；突變運算子：swap / insert
* 優點：天生不會產生重複或遺漏個案，硬約束處理單純

### 初始族群
混入數個貪婪解可大幅加速收斂：

* 依時間窗最早者優先排入
* 依長照等級由高至低排入
* 依地理鄰近度分群後排入

### 局部搜尋（Memetic GA）

純 GA 在 VRP 類問題上收斂緩慢，須加入局部搜尋：

* **relocate**：將一個個案搬移至另一條路線
* **swap**：交換兩條路線上的個案
* **2-opt***：跨路線的路段交換

### 求解流程

```
初始族群（貪婪解 + 隨機解）
   ↓
評估適應度（目標函數 − 罰分）
   ↓
選擇 → 交配 → 突變
   ↓
局部搜尋改良
   ↓
不可行解修復
   ↓ （未達終止條件則回到評估）
輸出最佳排班方案
```

## 6. LLM
### (1) 前處理：非結構化需求 → 結構化約束

現實中「阿嬤怕狗」「需要女性居服員」「三樓無電梯，需體力較好者」
「這位長輩比較怕生，要個性溫和的」這類資訊都寫在自由文字的備註欄，
僅存在於資深排班人員的經驗與記憶中。

**性格匹配即歸屬於此** —— 性格不像技能與性別可二值判定，
難以事先定義成固定欄位與匹配規則，因此現階段僅於資料中儲存性格標籤，
不納入罰分計算，改由 LLM 於前處理階段依個案敘述產生對應的軟約束。

以 LLM 將其抽取為機器可讀的約束條件後輸入 GA，
是 LLM 在本系統中**最不可取代、且痛點最真實**的應用。

### (2) 後處理：排班結果的決策解釋

將求解結果翻譯為自然語言說明：

* 為什麼這位居服員被指派至此個案
* 「若將 A 個案改由小美服務，將增加 25 分鐘轉場時間、公平性指數下降 0.1」

直接呼應競賽題目三「AI 營運效益決策視覺化應用」，
並建立管理者對 AI 排班結果的信任感。

### (3) 互動式改單

管理者以自然語言輸入「小明明天請假」，
由 LLM 轉換為約束變更，並觸發**局部重排**（而非全域重跑）。

---

## 7. 動態重排

臨時請假、個案取消、服務延誤等突發狀況發生時，**不重跑全域求解**：

* 僅取**受影響的路線**與**地理鄰近的數條路線**進行局部修復
* 以上一版排班結果作為 **warm start**，種入 GA 初始族群

### 效益

* **回應速度**：秒級回應，管理者可即時處理突發狀況
* **排班穩定性**：不會因單一異動導致全日排班大幅重洗 ——
  這是實務上管理者與居服員最在意的一點
