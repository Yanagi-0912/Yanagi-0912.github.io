## 一、常見提問與答法

### Q1：這些數字是中化的實際營運數據嗎？

不是。全部來自本團隊自建的排班雛型，測資為模擬資料
（6 名居服員、20 位個案、25 件當日案件）。

**但拆解的方法可以直接套用到實際資料上** ——
系統上線後只需要公司已有的派案紀錄、員工班表、個案時間窗與長照等級。

### Q2：43% 的非服務時間，聽起來是排班沒排好？

那 43% 是**最佳化之後**的結果。同一批案件與人力，
人工排班只會更差。這個數字標示的不是失誤，
而是**時間窗結構造成的改善空間上限在哪裡**。

### Q3：為什麼有案件排不進去？是人力不足嗎？

不是。未排入的 4 件只需要 195 分鐘服務，
而當日有 796 分鐘的可出勤時段沒被使用 —— 人力是需求的 4.1 倍。

排不進去的原因分三類，系統會逐件說明：

* **時段擠壓** —— 案件集中在早上尖峰，同一時段人手已滿
* **技能瓶頸** —— 例如管路照護只有 2 名居服員具備資格
* **時間窗錯位** —— 傍晚的案件無人仍在班

### Q4：AI 排出來的班，管理者為什麼要相信？

三個機制：

1. **θ 旋鈕** —— 營運與員工的取捨由管理者決定，不是 AI 決定
2. **LLM 決策解釋** —— 每個指派都能問「為什麼是他」
3. **可手動改單** —— 改完只做局部重排，不會把全日班表重洗

### Q5：全日案（8 小時）怎麼處理連續工時上限？

`T_c` 為 4 小時，單筆 8 小時的案件在演算法上視為
**法定休息於個案家中進行、服務不中斷**，以上限計入壓力指數。

> 此為本團隊的建模假設，實務認定需與公司確認。

### Q6：導入要多久？失敗風險多高？

Phase 1（數位化）**不需要 AI 即有價值** ——
紙本數位化、彈性打卡、家屬即時查詢本身就能減少行政與電話往返。
Phase 2 使用 Phase 1 累積的資料，不是另起爐灶。

**不是賭 AI 成功才有回報。**

### Q7：為什麼不用穿戴式裝置蒐集資料？

見本檔「三、評估後未採用的構想」。

## 二、演算法細節

### 問題形式化

每位居服員的一日行程構成一條路線，屬 **multi-depot VRPTW**：

```
住家（起點） → 個案 → 個案 → … → 住家（終點）
                └── 首末段為通勤，不計成本與工時 ──┘
```

* 決策變數 `x_{w,i,j} ∈ {0,1}`：居服員 w 是否從個案 i 直接前往個案 j
* 決策變數 `s_j`：個案 j 的實際開始服務時間

### 可行邊剪枝

```
邊 (i → j) 存在  ⟺  e_i + d_i + τ(i, j) ≤ l_j
```

以最早開始時間加上服務時長與轉場時間，若仍晚於下一案的最晚開始時間，
則此銜接在任何情況下都不可行，該邊直接刪除。

> 本測資：600 條候選邊剪枝後保留 236 條，**砍掉 61% 搜尋空間**。

### 目標函數

```
max   F = (1 − θ) * Π_norm  −  θ * P  −  ρ * u

  Π      = Σ_j r_j − Σ_w C_w − c_travel        當日毛利（元）
  Π_norm = Π ÷ Π_ref                           Π_ref = 當日所有案件收入總和
  P      = λ1*P_fair + λ2*P_pref + λ3*P_idle   ∈ [0, 1]
  θ      ∈ [0, 1]                              營運 ↔ 員工 的取捨
  u      = 未排入案件數 ÷ 總案件數              ρ 為固定懲罰係數（暫定 0.5）
```

> **月薪為沉沒成本**：月薪居服員的當日成本無論是否排入案件皆須計入。
> 若僅計入有排班者，會得出「讓月薪員工請假可提高毛利」的錯誤結論。

> `ρ * u` 不可省略：當 θ = 1 時毛利權重為 0，
> 若無此項，「什麼都不排」會成為最佳解。

### 壓力指數

```
S_w = α1*U_w + α2*L_w + α3*C_w        α1+α2+α3 = 1，S_w ∈ [0,1]
```

| 項 | 定義 | 意義 |
| --- | --- | --- |
| `U_w` | 當日總工作時數 ÷ `H_max` | 工時飽和度 |
| `L_w` | `Σ ω(g_j)*d_j` ÷ (`ω_max` × `H_max`) | 照護強度負荷 |
| `C_w` | 最長連續工作時數 ÷ `T_c` | 連續疲勞 |

### 罰分

| 項 | 定義 |
| --- | --- |
| `P_fair` | 全體壓力指數 `S_w` 的標準差 ÷ 0.5 |
| `P_pref` | Σ 各案件偏好違反分 ÷ 當日案件數 |
| `P_idle` | 全體空班分鐘總和 ÷ 全體在勤時間總和 |

偏好違反分：有指定居服員但未指派 = 1.0；未延續前次居服員 = 0.4；其餘 = 0。

### 硬約束與軟約束

| 硬約束（由編碼或修復保證） | 軟約束（計入罰分） |
| --- | --- |
| 服務時間窗 | 未指派指定居服員 |
| 同一居服員時段不得重疊 | 未延續前次居服員 |
| 排除／黑名單居服員 | 壓力指數分配不均 |
| 技能、性別需求 | 空班時間 |
| 法定工時上限與休息時間 | 性格配對度（由 LLM 前處理產生） |
| 轉場時間可行性 | — |

> 硬約束若僅以罰分處理，族群中將充滿無效解，GA 難以收斂。

### GA 設計

* **染色體** = 當日所有案件的一個排列（giant tour）
* **解碼** = 依序將案件插入邊際成本最低且可行的路線
* **交配** OX ／ PMX；**突變** swap ／ insert
* **初始族群** 混入貪婪解：時間窗最早優先、長照等級由高至低、地理鄰近分群
* **局部搜尋**（Memetic GA）：relocate ／ swap ／ 跨路線 2-opt*

### 動態重排

臨時請假、個案取消、服務延誤時**不重跑全域求解**：

* 僅取受影響路線與地理鄰近的數條路線進行局部修復
* 以上一版排班結果作為 **warm start** 種入初始族群

## 三、評估後未採用的構想

### 穿戴式裝置與物聯網

**不納入第一階段**，理由：

* 在長者身上加裝置的家屬同意流程與設備成本，不適合作為導入起點
* 排班參數所需的「實際服務時長」，Phase 1 的 App 彈性打卡即可取得，
  **不需額外硬體**
* 緊急通報／跌倒偵測屬於另一條產品線，與本次三個競賽題目不直接相關

> 原構想曾包含「將服務數據販售予機器人公司用於訓練 AI」。
> 涉及長者個資與照護倫理，與中化「自在享老、以人為本」的理念衝突，已捨棄。

### 接送車輛廣告版位

* 車上張貼廣告獲取額外收入；無外部廣告時張貼本司服務廣告
* 收益量級相對排班效益極小，不列入主要產出論述

### 外送平台式的人力媒合

* 照服員有結訓證明與登錄的法規門檻，無法直接類比即時媒合平台
* 保留於 Future Vision，但須有法規與訓練認證配套

## 四、資料與參數的已知限制

| 項目 | 現況 | 影響 |
| --- | --- | --- |
| **時薪表** | 240～450 元／小時（依長照等級），由原半日／全日固定價表反推估算 | 影響所有金額，須以實際費率校準。**無級距折扣：收費 = 時薪 × 時數** |
| **照護強度權重 ω(g)** | 示意值 | Phase 1 由資深排班人員填寫，Phase 2 以服務紀錄回歸校準 |
| **GA 隨機性** | 單日毛利多次求解間約 ±5% 浮動 | 簡報引用值取多次求解的中位數 |
| **地點** | 抽象平面座標，`τ(i,j) = 歐氏距離 ÷ 車速` | 接地理編碼 API 時只需替換距離計算函式 |
| **LLM** | 雛型的對話窗口為規則式模擬 | 正式版依演算法文件 §6 接入 |
| **最低件數約束** | 演算法未納入「每人每日至少 N 件」 | 目前僅能透過 θ 間接達成，建議補為軟約束 |

### 使用方式與範圍

**一、雛型程式碼（`public/projects/care-scheduling/`）**

* `data.js` —— 模擬測資生成：20 位服務個案的姓名、地址、抽象座標、技能與性別需求、
  指定／黑名單居服員、25 件當日案件的時間窗與服務時長。
  **測資規格（案件數、服務時長分布、半日／全日分界）由團隊指定**，AI 僅依規格生成內容。
* `solver.js` —— 單筆服務時長超過連續工時上限（全日案）時的處理邏輯。
* `app.js` —— 居服員即時狀態（尚未上班／待命中／已下班）的判定、
  收費計算改為由服務時長推導、時間單位一致性修正。
* 演算法主體（GA 編碼、目標函數、罰分、壓力指數、解碼器）依團隊自訂之設計文件實作，
  AI 未變更其設計。

**二、數據分析**

以 Node 腳本執行下列分析，結果用於簡報：

* θ 權重掃描（毛利、`P_fair`、未排入件數）
* GA 與五種貪婪法的比較、GA 收斂世代量測
* 可出勤時間的產能拆解（服務／轉場／班內空班／未使用時段）
* 薪資結構 × 收費等級 × 轉場時間的邊際毛利推導

**三、文件撰寫**

* 「簡報草稿.md」的頁面結構規劃與文字撰寫
* 本附錄的撰寫
