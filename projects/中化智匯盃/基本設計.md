## 函數

### 參數定義

| 參數 | 說明 | 暫定值 |
| --- | --- | --- |
| `H_max` | 當日工時上限 | 8 小時 |
| `T_c` | 連續工時上限 | 4 小時 |
| `ω(g)` | 長照等級 g 的照護強度權重 | 見下表 |
| `ω_max` | `ω(g)` 的最大值 | 2.0 |

| 長照等級 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `ω(g)` | 1.0 | 1.2 | 1.3 | 1.5 | 1.6 | 1.8 | 2.0 |

> 數值為示意值，須以實務校準：
> **Phase 1** 由資深排班人員依經驗填寫，將隱性知識顯性化；
> **Phase 2** 以累積的服務紀錄回歸校準（實際耗時超出預估之比例、加班率、請假率）。

### 壓力指數

> S_w = α1*U_w + α2*L_w + α3*C_w
> （α1 + α2 + α3 = 1，S_w ∈ [0, 1]）

| 項 | 定義 | 意義 |
| --- | --- | --- |
| `U_w` | 當日總工作時數 ÷ `H_max` | 工時飽和度：今日工時額度用掉多少 |
| `L_w` | `Σ ω(g_j)*d_j` ÷ (`ω_max` * `H_max`) | 照護強度負荷：服務的個案有多重 |
| `C_w` | 最長連續工作時數 ÷ `T_c` | 連續疲勞：是否一路做到底沒有喘息 |

三項皆已正規化至 0~1，因此 α 權重僅代表各維度的相對重要性，
不需兼任單位換算；S_w 亦落在 0~1，可直接以百分比顯示於介面，
`P_fair` 取標準差才具意義。

`L_w` 的分母 `ω_max * H_max` 代表「整日服務最重度個案」的理論負荷上限，
使不同居服員、不同日期之間的壓力指數可互相比較。

#### 工時的認定

* 工作時數 = 服務時數 + 轉場時數
* **空班（等待）時間視為休息，不計入工時**
* 空班達 30 分鐘以上者視為法定休息，中斷連續工時的累計；未達 30 分鐘者不中斷
* 首末段通勤不計費亦不計工時（詳見"居服員排班演算法.md"）

#### 適用範圍

* 壓力指數為**當日**指標，**不跨日累積**
* 排班階段計算的是整條路線跑完的**預估值**；
  管理端儀表板顯示的是當下的**累計實際值**。兩者為同一公式、不同時間窗
* **連續工作超過 `T_c` 為違法**，屬硬約束，不得以壓力指數的罰分替代

### 罰分（即目標函數中的軟約束罰分項）

> P = λ1*P_fair + λ2*P_pref + λ3*P_idle
> （λ1 + λ2 + λ3 = 1，P ∈ [0, 1]）

| 項 | 定義 | 意義 |
| --- | --- | --- |
| `P_fair` | 全體居服員壓力指數 `S_w` 的標準差 ÷ 0.5 | 壓力分配不均（工時分配不均已含於壓力指數中） |
| `P_pref` | Σ 各案件偏好違反分 ÷ 當日案件數 | 個案偏好未滿足 |
| `P_idle` | 全體空班分鐘總和 ÷ 全體在勤時間總和 | 空班（等待）時間 |

#### 偏好違反分

| 情形 | 分值 |
| --- | --- |
| 有指定居服員，但未指派該員 | 1.0 |
| 無指定居服員，且未延續前次居服員 | 0.4 |
| 其餘（偏好已滿足） | 0 |

#### 說明

* `P_fair` 的分母 0.5 為 0~1 區間內標準差的理論最大值（全體呈兩極分布時），
  使 `P_fair` 落在 0~1
* `P_idle` 的分母「在勤時間」指該居服員首案開始至末案結束的跨度，
  空班 = 在勤時間 − 工作時數，因此 `P_idle` 天然落在 0~1
* 空班時間雖視為休息、不計入工時，但對居服員而言是無收入的等待、
  對公司而言是閒置的人力，故仍計入罰分
* 三項皆為 0~1 的無量綱指標，`P` 亦落在 0~1，
  可與正規化後的毛利直接加權（見「居服員排班演算法.md」§3）

### 待辦

* **長期公平性指標**：現行壓力指數僅衡量當日負荷，未涵蓋連續上班天數造成的累積疲勞。
  待長期服務資料累積、需求波動分析完成後，再評估加入
  「近 7 日平均壓力指數」或「連續上班天數」作為跨日公平性指標。
* `ω(g)` 權重表的實證校準（併入 Phase 2 資料分析）。

## 資料庫設計

> 正式的正規化 schema 於 Phase 1 實作時設計。
> 以下為 **Demo 雛型的前端資料模型** —— UI 與演算法共用同一組物件，
> 避免畫面與演算法各自長出一套資料格式。

### 通用約定

| 項目 | 約定 |
| --- | --- |
| 時間 | 一律以「距零時的分鐘數」整數表示（`7:30` → `450`），顯示時再格式化為 `HH:MM` |
| 地點 | Demo 階段使用抽象平面座標 `{x, y}`（單位：公尺）；`address` 欄位僅供顯示 |
| 轉場時間 | `τ(i,j) = 歐氏距離 ÷ 平均車速`，無條件進位至 5 分鐘 |
| 金額 | 新台幣元 |

> 未來改接地理編碼與路徑規劃 API 時，只需替換 `travelTime(a, b)` 這一個函式，
> 其餘資料結構與演算法完全不動。

### 參數 PARAMS

```js
const PARAMS = {
  H_max: 480,          // 當日工時上限（分鐘）
  T_c:   240,          // 連續工時上限（分鐘）
  restThreshold: 30,   // 空班達此長度視為休息，中斷連續工時累計
  speed: 300,          // 平均車速（公尺／分鐘）
  travelCostPerMeter: 0.005,   // 交通成本（元／公尺）

  omega:    { 2:1.0, 3:1.2, 4:1.3, 5:1.5, 6:1.6, 7:1.8, 8:2.0 },
  omegaMax: 2.0,
  revenue: {
    half: { 2:340, 3:420, 4:460, 5:525, 6:565, 7:605, 8:645 },
    full: { 2:675, 3:840, 4:920, 5:1045, 6:1130, 7:1210, 8:1285 },
  },

  alpha:  [0.3, 0.5, 0.2],   // 壓力指數三項：U_w, L_w, C_w
  lambda: [0.4, 0.4, 0.2],   // 罰分三項：P_fair, P_pref, P_idle
  theta:  0.3,               // 營運 ↔ 員工 取捨（0 = 純毛利，1 = 純公平）

  prefPenalty: { designatedMissed: 1.0, continuityBroken: 0.4 },
};
```

### 當日案件 case

```js
{
  id: '20260821-001',                       // 案件編號 = 日期 + 流水號
  clientId: 'C001',
  date: '2026-08-21',
  serviceType: 'half',                      // 'half' | 'full'
  window: { earliest: 420, latest: 430 },   // 最早／最晚可開始
  duration: 90,                             // 服務時長（分鐘）
  revenue: 565,                             // = PARAMS.revenue[serviceType][careLevel]
  assignedTo: null,                         // 排班結果回填
  actual: { arrivedAt: null, finishedAt: null },   // 居服員 App 打卡回填
}
```

> * 長照等級、地點、偏好等資料由 `clientId` 關聯取得，不在案件中重複儲存
> * `serviceType` 只決定收費級距，實際服務時長仍以 `duration` 為準
